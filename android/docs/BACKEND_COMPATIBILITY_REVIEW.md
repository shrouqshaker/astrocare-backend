## 1. الحكم السريع

| المحور | النتيجة |
|---|---|
| ملفات `contracts/` (schemas, examples, vectors, data) | **متطابقة بايتًا ببايت** مع نسخة Android |
| `POST /api/v1/sync/batch` (الطلب، الرد، الأخطاء، التكرار) | **متوافق** بعد إصلاح 3 عيوب في Android |
| المصادقة، الرابط، `deviceId`، الطوابع الزمنية، الحدود | **متوافق** |
| الـ seed التجريبي | **متطابق**؛ الخادم المنشور عليه 126 قياسًا + check-in واحد مطابقين تمامًا |
| `GET /rules/latest` و`GET /guides/latest` | متوافقان، لكن التطبيق لا يستدعيهما (الأصول مضمّنة داخله) |
| `GET /trends` و`GET /overview` | **امتداد غير موجود في العقد الأصلي**، والتطبيق لا يستخدمهما حاليًا؛ توجد فروق تفسيرية لو تم دمجهما لاحقًا |
| AI/Data parity (UUIDv5 / alerts) | **كان غير متوافق** في توليد معرّفات التنبيهات؛ تم إصلاحه في Android |
| جاهزية الإنتاج | ليست جاهزة: مفتاح API تجريبي، لا مصادقة مستخدم، لم تُجرّب على جهاز فعلي |

**الخلاصة:** الـ backend متوافق مع شغل الأندرويد على مستوى العقد والمزامنة بعد الإصلاحات أدناه. لا يحتاج الـ backend إلى تعديلات لكي يعمل التطبيق. المتبقي الأساسي هو التزام تشغيلي (تحميل الـ seed على أي قاعدة جديدة) وفروق analytics غير مستخدمة حاليًا.

## 3. عيوب توافق وُجدت في Android وتم إصلاحها

### 3.1 أخطر عيب: حقول `items` الفارغة كانت تُحذف من الـ payload

`SyncItemsDto` كان يعرّف المصفوفات الثلاث بقيم افتراضية `emptyList()`، و`Json` الافتراضي في kotlinx يستخدم `encodeDefaults = false`. النتيجة الفعلية التي أثبتها اختبار جديد:

```json
"items":{"measurements":[{...}]}
```

أي أن `symptomCheckins` و`alerts` **غير موجودين** عندما تكون فارغة. مخطط الخادم `sync-request.schema.json` يطلب الثلاثة صراحةً (`required`)، لذا كان أي batch لا يحتوي على العناصر الثلاثة معًا سيُرفض بـ **400 VALIDATION_ERROR** قبل معالجة أي عنصر. هذا كان سيحدث في معظم عمليات المزامنة.

**الإصلاح:** `@EncodeDefault` على المصفوفات الثلاث في `SyncItemsDto`، وعلى `TriggeredByDto` (الذي يطلبه `alert.schema.json` أيضًا). أُضيف اختبار يثبت وجود `symptomCheckins` و`alerts` دائمًا.

### 3.2 معرّفات التنبيهات كانت عشوائية بدل UUIDv5

كان `RuleEngine` يولّد `UUID.randomUUID()` لكل تنبيه. مرجع AI/Data والـ backend يستخدمان UUIDv5 ثابتًا:

```text
namespace = 6f5d1a0e-6f2c-4f4b-9a0f-1d7c2b3e4a55
name      = alert|{astronautId}|{ruleId}|{revision}|{sorted measurementIds},{sorted checkinIds}
```

نفس التنبيه كان سيأخذ ID مختلفًا في Android عنه في `/overview` أو `/trends`، مما يسبب تكرار السجلات عند أي دمج لاحق (وهو ما حذّر منه `docs/AI-DATA-INTEGRATION.md`).

**الإصلاح:** أُضيف `StableUuid` بنفس الخوارزمية، وأصبح `AlertAssembler` يستخدمه، مع ترتيب `triggeredBy` IDs مثل الخادم. تم التحقق من القيم المرجعية:

- `v5("test") = 0565a3b2-100b-5ef6-ba25-fd0842c4fb01`
- تنبيه `HR-HIGH-W` من fixture الـ parity = `6ce4d0e5-d55f-517f-86c1-7c8a5703cfe3`

### 3.3 إقرار التنبيه بعد مزامنته لم يكن يصل للخادم

`AlertDao.acknowledge` كان يحدّث `acknowledgedAt` فقط دون تغيير `localSyncStatus`. لو كان التنبيه قد سُجّل `synced` سابقًا فلن يدخل batch تالٍ، وبالتالي لن يرى الخادم الإقرار أبدًا. الخادم يدعم الإقرار فقط عبر batch فيه نفس التنبيه (duplicate + `acknowledgedAt`).

**الإصلاح:** الإقرار الآن يعيد التنبيه `synced` إلى `pending` مع مسح `syncError`، ويترك التنبيه `rejected` كما هو (لأنه لم يُخزَّن على الخادم أصلًا). أُضيف اختباران في Room يغطيان الحالتين.

## 4. فروق متبقية وليست أعطالًا في المزامنة

### 4.1 الـ seed مسؤولية تشغيلية

Android يعلّم صفوف الـ seed كـ `synced` ولا يرفعها. هذا صحيح فقط إذا كانت قاعدة الخادم محمّلة بنفس الـ seed. الخادم المنشور حاليًا محمّل ومطابق، لكن أي قاعدة جديدة أو بعد `replace` تحتاج:

```bash
npm run seed
```

بدون ذلك ستظل 126 قياسًا موجودة محليًا فقط. يُفضّل إضافة فحص بدء تشغيل في الخادم أو توثيق هذا الشرط بوضوح أكبر في دليل النشر.

### 4.2 تحليلات `/overview` و`/trends` غير مستخدمة من التطبيق

التطبيق لا يستدعي أيًا من `rules/latest`, `guides/latest`, `/trends`, `/overview`, أو مسارات التاريخ. التقييم والاتجاهات والأدلة كلها محلية. لذلك لا يوجد تعارض حالي، لكن لو تم دمج التحليلات لاحقًا فهناك فروق تفسيرية يجب حلها أولًا:

| الموضوع | Android | Backend |
|---|---|---|
| تصفية القياسات غير الصالحة | يستبعد القيم خارج min/max ويكمل للقياس الأقدم الصالح | `context.service.js` لا يصفّيها؛ يستخدم آخر قياس داخل النافذة |
| عتبة evidence للـ insight | `threshold = baselineMean` | `baselineMean + sign(z) × zThreshold × scale` |
| نافذة "latest" للـ insight | آخر قراءة داخل نافذة 24 ساعة | آخر قراءة داخل نافذة 7 أيام |
| معرّفات الـ insights | لا يوجد `id` في نموذج `Insight` | UUIDv5 `insight|...` |
| `generatedBy` | `android_local` | `backend_optional` |

هذه ليست مشكلة في المزامنة ولا تؤثر على شاشات التطبيق الحالية. إن كان المطلوب توحيد `/trends` و`/overview` مستقبلًا، فهي قائمة عمل منفصلة.

### 4.3 قيود الخادم المعروفة

- `X-API-Key` تجريبي وليس مصادقة مستخدم؛ التطبيق يستخدم `demo-key` الافتراضي.
- الخادم يخدم `demo-astronaut-01` فقط لمسارات التاريخ والـ seed؛ التطبيق يستخدم نفس الـ ID افتراضيًا ولا يسمح بتغييره من الواجهة.
- لا يوجد endpoint للإعدادات أو الأدلة العربية أو الصور؛ التطبيق يعتمد على أصوله المحلية.
- لم تُجرّب المزامنة من جهاز Android فعلي إلى الخادم؛ التحقق تم عبر HTTP مباشر وعبر اختبارات JVM/Robolectric.

## 5. ما يجب فعله الآن

1. **لا تعديل مطلوب في الـ backend** لتشغيل المزامنة الحالية.
2. تأكد أن قاعدة الخادم محمّلة بالـ seed (`npm run seed`) قبل أي عرض جديد.
3. استخدم APK المحدّث المرفق مع هذه المراجعة (يحتوي إصلاحات الحقول والمعرّفات والإقرار).
4. إذا أردتم دمج `/overview` أو `/trends` في التطبيق، نبدأ بجدول الفروق في §4.2 ونوحّد التفسيرات قبل الدمج.
5. قبل الإنتاج: استبدال مفتاح الديمو بمصادقة حقيقية، واختبار جهاز فعلي، ومراجعة طبية للحدود التجريبية.
